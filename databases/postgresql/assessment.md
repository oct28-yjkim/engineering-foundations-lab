# PostgreSQL 완료 기준과 전문가 수준 검증

## 공통 필수 운영 관문

[운영 runbook](operations.md)의 실제 서버 정상 기준선 1개, 서로 다른 사건 최소 2개, 각 사건의 경쟁 가설 2개 이상·원시 지표/로그·제한된 조치·되돌림/회복 후 업무 검산을 제출합니다. 지표는 gauge/counter/event, 단위·집계 창·reset 여부를 표시합니다. 임계값 암기나 dashboard 화면만으로는 통과하지 않습니다.

원리 모형·손계산·mock/단위 테스트는 선택 보조 증거입니다. 이를 생략했다고 운영 과정 진입을 막지 않으며, 성공했다고 실제 운영 점수를 주지도 않습니다. 기존 점수 기준 및 제품별 정확성·복원·권한 관문은 유지합니다. 환경이 없으면 설계/원리 학습 완료와 운영 미완료를 구별하고, 실제 baseline/사건 증거 없이 전체 운영 완료를 선언하지 않습니다.


이 과정의 완료는 업무 판단을 검증하는 것이며 직함·경력을 보증하지 않습니다. 설명을 잘하는 것, 실험을 실행한 것, 복구를 실제 성공시킨 것은 서로 다른 증거입니다. [공통 실험 방법](../shared/experiment-method.md)과 아래 관문을 함께 적용합니다.

## 상태 표기

각 모듈의 S/E/T/B 과제마다 `미착수`, `설계 완료`, `실행 완료`, `동료 재현 완료`를 구분합니다. 환경이 없으면 T/B를 미완료로 남기고 구성 사양·예상 증거·판정 쿼리를 제출합니다. 예측 결과를 측정 결과 칸에 채우지 않습니다.

| 평가 영역 | 배점 | 최소 요건 |
| --- | --- | --- |
| 정확성·불변식 | 25 | 손계산/독립 oracle로 금액·중복·시간·동시성·복원 결과를 검산하고 정상/경계/실패 입력을 구별 |
| 원리·내부 동작 | 25 | snapshot/WAL/planner/vacuum 경계를 자기 언어로 설명하고 반례와 버전 일치 소스 연결 |
| 재현·실험·반증 | 25 | 환경·데이터·설정·세션 순서·원본 로그가 있고 독립 변수를 통제. 최종 성능 비교는 warmup 제외 조건별 20회 이상, 경쟁 가설과 자원 비용도 비교 |
| 운영 판단·복구·전달 | 25 | 재시도·실패 경계·실제 restore·RPO/RTO 검산, 채택/기각/rollback 근거. 다른 사람이 재현할 수 있는 runbook과 설명 |

**총점 80점 이상, 영역별 15점 이상, 해당 단계의 필수 관문 전부 통과**가 기준입니다. 총점이 높아도 동시성 불변식이나 복원에 실패하면 상쇄할 수 없습니다. 설명만 있는 영역은 실행을 요구하는 관문을 통과한 것으로 채점하지 않습니다.

## 필수 관문

| 관문 | 제출 증거 | 통과 판정 |
| --- | --- | --- |
| G1 · SQL 정확성 | NULL·중복·JOIN fan-out 반례, seed invariant 검산, query 의미 정의 | 손계산과 실제 결과 일치. 금액·시간·동률 정렬 의미를 명시 |
| G2 · 저장·내구성 | 페이지/크기 관측, WAL·buffer·LSN 실험, commit 순서도 | rollback 후 WAL 존재와 WAL-before-data를 설명. page raw 실측이 없으면 E 미완료 표시 |
| G3 · 동시성 | RC/RR 시간표, RR write skew, SSI 40001, deadlock 40P01, retry 의사코드 | 전체 transaction 재시도와 재판단으로 불변식 유지. 오류 문장만 재실행하지 않음 |
| G4 · 계획·자원 | 추정 오차 표, 통계/인덱스 비교, spill·병렬 메모리 분석 | 같은 결과를 유지하며 총 작업과 비용 설명. 강제 설정과 자연 선택 구별 |
| G5 · 정리·운영 | HOT 반례, 장기 snapshot 전후 vacuum, 장애 3종 진단 | 원인 3개를 실제 증거로 구별. 누적 통계/추정치의 한계 명시 |
| G6-S · 논리 복원 | 별도 DB restore 로그·카운트·업무 금액/참조 검사·소요 시간 | 원본을 보존하며 검산 성공. dump 생성만으로 통과 불가 |
| G6-T · PITR | base/WAL/목표/timeline, 정상 A/B·잘못된 변경·sentinel C 검증, 두 번째 재복원 | 정상 commit 보존, 목표 뒤 변경 제외, archive 누락 탐지. 실제 RPO/RTO 기록 |
| G7-T · 복제 | physical replay 지연, logical slot retention, failover·fencing·외부 원장 대조 | ACK/flush/replay 차이와 손실 여부 입증. 새 primary와 old primary의 쓰기 경계 명확 |
| G8-B · 구현 | runtime/source SHA, debug/test 로그, 두 입력의 stack·상태 차이, 최소 테스트 | 3개 구현 경로 설명 및 최소 1개 실제 debugger/테스트 재현 |
| G9 · 종합 판단 | M14 캡스톤·벤치마크 원본·장애/복원 runbook·동료 재현 | 재고/금액/중복 불변식 유지, 오류 요청도 계수, 미검증 영역 명시 |

기초(M01–04)는 G1–G2, 내부 동작(M05–10)은 G3–G5를 추가로 통과합니다. 단일 노드 운영 완료는 G6-S와 G9의 S 영역을 포함합니다. **고급 검증 완료는 G6-T/G7-T/G8-B를 포함한 모든 관문과 동료 재현**이 필요합니다. 단일 노드 완료를 전체 과정 완료로 바꾸어 적지 않습니다.

## 캡스톤 제출물

M14의 재고·주문 문제에서 제출할 구조의 예입니다. 이는 학습자가 생성할 산출물 구조이며 현재 이미 측정 결과가 들어 있다는 뜻이 아닙니다.

```text
postgresql-capstone/
  environment.txt          # runtime·digest·설정·제약·소스 SHA
  design.md                # 불변식·transaction·index·선택/기각 이유
  schema.sql               # 별도 capstone_pg schema
  workload/                # seed·요청·재시도·검산 도구
  evidence/
    concurrency/           # 정확한 A/B 순서와 SQLSTATE
    plans/                 # 비교 전후 원본 EXPLAIN
    benchmark/             # warmup 구분, 모든 실행·오류·지연
    recovery/              # 백업·복원·LSN·timeline·검산
  runbooks/                # 탐지→판별→조치→복구 확인→되돌림
  source-notes.md          # 함수/상태/불변식/실제 관측
  review.md                # 동료 재현, 실패와 수정 이력
```

벤치마크에는 결과가 좋은 실행만 선택하지 않습니다. 요청 전체 지연과 SQL 실행 시간, 성공/실패/재시도, throughput과 concurrency를 함께 기록합니다. 작고 warm한 fixture의 개선을 실제 수백 GB 운영환경의 개선이라고 확대하지 않습니다. 생산 부하를 모사하려면 분포·working set·동시성·스토리지 차이를 먼저 기술합니다.

## 구두 방어와 미지의 문제

리뷰어는 다음 중 최소 5개를 골라 답변을 듣고 각 답에 새로운 조건을 하나 추가합니다. 예를 들어 “인덱스가 있다” 다음에 “통계가 오래됐고 prepared statement를 사용한다”를 추가합니다.

1. COMMIT이 성공했는데 replica의 조회에 행이 없다. 가능한 세 원인과 판별 방법은?
2. 모든 query가 shared hit인데 p95가 높다. 다음으로 볼 지표와 이유는?
3. VACUUM이 돌았는데 용량이 줄지 않는다. 정상과 장애를 어떻게 구별하는가?
4. covering index를 추가한 뒤 읽기는 빨라지고 쓰기는 느려졌다. HOT·WAL·VM을 연결해 설명하라.
5. SERIALIZABLE 오류율이 올랐다. 격리를 낮추기 전에 어떤 실행 순서와 불변식을 확인해야 하는가?
6. pg_verifybackup이 통과했지만 실제 restore가 실패했다. 검사 범위 차이는?
7. 실행 계획의 rows 추정이 정확해졌는데 시간은 그대로다. 이 개선의 가치는 무엇인가?
8. logical slot이 inactive이고 WAL이 증가한다. 삭제·재개·재동기화의 선택 기준은?
9. 장애조치 후 old primary가 돌아왔다. endpoint 변경만으로 해결되지 않는 이유는?
10. 같은 SQL이 PG18 minor 업데이트 뒤 다르게 실행된다. source·통계·설정·plan 중 무엇을 어떻게 분리할 것인가?

정답 문구보다 판별 가능한 가설, 가장 적은 위험으로 얻을 증거, 결론의 한계를 평가합니다. 모르는 구현 경계는 모른다고 밝히고 검증 절차를 제시해야 합니다.

## 재평가

실패한 관문은 같은 답을 외워 제출하지 말고 데이터 분포·세션 순서·장애 지점을 하나 바꿔 다시 수행합니다. 수정 전후를 보관하고 원래 설명이 왜 틀렸는지 기록합니다. 고급 검증 이후에도 새 workload·버전·운영 장애에서 이 과정을 반복하는 것이 전문성을 유지하는 방법입니다.
