# 기본 LAB 규격 — 정상 동작부터 진단·복구까지

[시작 안내](README.md) · [기록 양식](incident-report-template.md) · [실행형 예시: OpenSearch](../search/opensearch/labs/README.md)

기본 LAB은 “장애를 많이 만드는 과정”도 “코드가 PASS를 출력하는 과정”도 아닙니다. **무엇을 하는 도구인지 직접 확인하고, 어떻게 동작하며 어디를 관측해야 하는지 익힌 뒤, 한계를 이해하고 흔한 문제를 진단·복구하는 과정**입니다. DB·검색·메시징·데이터 처리·관측·제품 분석·플랫폼·IaC·보안·MCP 16개 도구 트랙에 적용합니다. LLM 논문 실험의 CPU 기본 + GPU/API 선택 경로는 별도로 유지합니다.

## 1. 모든 LAB이 답해야 하는 여섯 질문

| 순서 | 학습자가 직접 할 일 | 반드시 남길 증거 |
| --- | --- | --- |
| 1. 정상 기능 | 작은 합성 입력을 넣고 조회/처리/변경/취소 결과 확인 | 예상 ID·값·순서·권한과 실제 결과; 성공 응답만으로 끝내지 않음 |
| 2. 동작 원리 | 요청이 거치는 저장·실행·전달·상태 전이 설명 | 입력 → 주요 단계 → 관측 가능한 출력; ACK·조회 가능·내구성 등 서로 다른 보장 구분 |
| 3. 모니터링 | 해당 경로의 API/SQL/CLI/UI/log를 직접 읽기 | 수집 방법, 단위, gauge/counter/event, 관측 창, 정상 값/분포, 누락과 reset |
| 4. 제약 | 한계 하나를 작은 반례로 확인하거나 조사 | 단일 노드/권한/판본/서비스 quota/일관성/자원/보존의 경계; 확인 못 한 항목은 미검증 |
| 5. 흔한 문제 | 정상 기준선 이후 실패 요인 하나만 적용 | 사용자 증상, 오류 층·코드, 경쟁 가설 두 개, 원인을 가르는 관측 |
| 6. 진단·복구 | 증거 보존 → 제한된 조치 → 같은 입력으로 재검증 | 조치 전후 값, 정확성·권한·누락/중복·후속 영향, 되돌림과 예방책 |

정상 기준선이 틀리거나 관측 방법을 모르면 장애를 추가하지 않습니다. 먼저 실패한 정상 기능부터 진단합니다. 학습 중 새 지표를 발견하면 3단계로 돌아가 의미를 조사합니다. **28주 심화·소스 연구는 기본 LAB의 선수 과정이 아닙니다.** 작은 정상 기능과 사건 두 개부터 완성하고, 원리 설명이 막힌 지점에서 해당 강의·소스를 깊게 읽습니다.

## 2. 실습 카드에 먼저 적을 계약

- **대상:** 정확한 version/revision, local/managed, endpoint·project·namespace·principal·소유자, 별도 준비물.
- **정상 기능:** 입력, 독립적인 기대 결과, 정상 실행 명령, 결과를 확인할 위치.
- **관측:** 신호 → 수집 명령/API/UI → 의미/단위/형식 → 경쟁 원인 → 수집 불가 조건.
- **제약 두 종류:** 제품 자체의 보장/한계와 이 LAB의 단순화/자원 상한을 분리합니다. “단일 노드로만 검증했다”는 제품이 확장 불가능하다는 뜻이 아닙니다.
- **사건:** 학습 목적에 맞는 입력 오류·권한 거부·대기·backlog·부분 성공·배치 불가 등 대표 사례, 주입 범위, 중단 조건.
- **복구:** 변경 대상과 값, 예상 부작용, 원복 방법, 처음과 같은 workload/정답의 재검산, 남는 데이터·설정.

“흔한 문제”는 입문자가 대비할 대표 운영 유형을 뜻합니다. 이 저장소가 제품별 사고 빈도 통계를 수집해 순위를 매긴 것은 아닙니다. 모든 오류가 재시도로 해결되지 않으며, 정상적인 권한 거부·동시성 충돌·가시성 지연을 서비스 장애와 구별하는 것도 학습 목표입니다.

## 3. 직접 실습과 조사를 함께 진행하기

먼저 현상을 예측해 적고 실행한 뒤, 예상과 다른 부분을 **해당 버전의 공식 API 문서 → 설정/릴리스 차이 → 고정 소스·테스트 → 필요하면 논문** 순서로 조사합니다. 조사로 알아낸 내용과 실제 관측을 별도 칸에 적습니다. `latest` 문서의 기본값을 설치한 버전의 사실로 단정하지 않습니다.

| 진행 상태 | 가능한 결과물 | 이 상태에서 주장하지 않을 것 |
| --- | --- | --- |
| 조사·설계 | 공식 출처·버전·예측·실행 절차·제약 정리 | 실제 제품 실행·장애 재현 성공 |
| 제공 기록 분석 | 출처/환경이 확인된 정제 로그·지표로 경쟁 가설 비교 | 자신이 직접 재현한 결과; 가상 로그를 실제 증거로 표시 |
| 정상 기능 실측 | 정답 비교 + 동작 설명 + 정상 관측 + 확인한 제약 | 장애 복구·운영 숙련 완료 |
| 사건 재현 | 특정 증상과 원인 구분 증거 | 복구 후 업무 결과를 아직 검증하지 않은 성공 |
| 회복 검증 | 같은 workload의 정확성·상태·오류 회복 | 다른 topology·권한·규모·SLO까지 보장 |

환경이 없는 조사도 유효한 학습입니다. 다만 실제 실행 상태로 승격시키지 않습니다. 제품별 문서가 **제공 코드 / 수동 절차 / 추가 환경 필요 / 실제 검증 이력**을 구분하도록 합니다. 관리형 계정이나 exporter/dashboard가 저장소에 자동 포함된 것으로 해석하지 않습니다.

## 4. 제약을 핑계로 핵심 경험을 빼지 않기

작은 단일 노드에서도 입력 오류, 부분 성공, 가시성, 잘못된 설정, 잠금·대기, 권한 경계 등 일부 문제는 실제로 경험할 수 있습니다. 반면 quorum·replica 승격·노드 확장은 다중 노드가 필요합니다. 작은 환경으로 증명할 수 없는 과제는 삭제하거나 Python 모형으로 대체했다고 하지 않고 **별도 환경 실습**으로 제공합니다.

예를 들어 [OpenSearch 단계형 사건](../search/opensearch/labs/incidents.md)은 실제 REST 오류·결과를 확인하고, [관측 LAB](../search/opensearch/labs/observation.md)은 실제 쿼리와 지표를 비교하며, [3→4노드 확장 LAB](../search/opensearch/labs/scaling-incidents.md)은 별도 Compose를 직접 선택합니다. 수동 write-block은 차단 상태를 확인하는 실습이지 디스크를 실제로 가득 채운 실험이 아닙니다. 작은 데이터의 query 비교도 실제 포화/429 재현과 다릅니다.

클라우드 생성·과금·실제 사용자 데이터 전송·운영 권한 변경·disk-full·quorum 상실은 기본 자동 실행에 넣지 않습니다. 더 큰 환경이 필요하면 목적, 비용/자원 예산, 대상 소유권, 종료 조건, 복구 방법을 정하고 별도로 선택합니다. 상한 때문에 증상이 나오지 않으면 “미재현”이 답이며, 성공을 만들기 위해 부하를 무제한으로 늘리지 않습니다.

## 5. 기본 LAB 완료 기준

정상 기능 한 묶음, 그 동작 원리 설명, 직접 수집한 정상 관측, 확인한 제약, 서로 다른 사건 두 개의 진단·복구 증거를 [기록 양식](incident-report-template.md)에 남깁니다. 복구 버튼 실행·process 재시작·health green·테스트 PASS만으로 완료하지 않습니다. 미수행 단계는 명시하고, 기본 LAB 완료와 28주 심화/HA/보안/부하 시험 완료는 각각 평가합니다.
